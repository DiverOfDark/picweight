# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository.

## Project Overview

picweight is a self-hosted AI-assisted calorie & БЖУ tracker. You photograph a
meal; a server-side bounded agentic loop (`rig` 0.41 on OpenAI) returns per-item
grams and macros; the app immediately tells you what budget is left today.
Single container: Rust backend + Vue 3 SPA + Android APK, deployed to Kubernetes
via Helm.

Read [`docs/PRD.md`](docs/PRD.md) before making design decisions — it states not
just what was built but what was deliberately *not* built, and why. Read
[`docs/rig-spike.md`](docs/rig-spike.md) before touching `backend/src/agent/`:
it is verified ground truth on the rig 0.41 API, which is newer than most
training data.

## Build & Development Commands

### Backend (Rust, in `backend/`)

```bash
cd backend && cargo run                    # dev server on :33100
cd backend && cargo build --release
cd backend && cargo test                   # unit + integration
cd backend && cargo test --lib agent       # one module
cd backend && cargo clippy --all-targets   # must be clean
cd backend && cargo run -- openapi ../android/openapi.json   # regenerate the API contract
```

`cargo test` includes the §13 integration suite in `backend/tests/`, which boots
the real router over a real TCP socket against a temp SQLite file, a mock IdP
(real OIDC discovery runs) and a mock LLM speaking OpenAI's Responses and Chat
Completions APIs. It also fails if `android/openapi.json` is stale — regenerate
it with the command above whenever a route or schema changes.

`picweight-backend openapi` must keep working with **no configuration at all**:
no database, no OIDC, no API key. The Docker build runs it in a stage that has
none of those.

### Frontend (Vue 3, in `frontend/`)

```bash
cd frontend && npm install
cd frontend && npm run dev      # Vite with HMR, /api proxied to :33100
cd frontend && npm run build    # → dist/
cd frontend && npm test         # vitest
```

### Android (Kotlin, in `android/`)

```bash
cd android && ./gradlew assembleDebug
cd android && ./gradlew assembleRelease   # signed when KEYSTORE_PASSWORD is set
```

JDK 17 (the Gradle toolchain pins it explicitly; local JDKs are newer). The
Retrofit client is generated by `org.openapi.generator` 7.20.0 from
`android/openapi.json` — never hand-edit the generated client, regenerate the
spec instead.

### Docker & Helm

```bash
docker compose up --build            # local full stack
helm lint helm/picweight
helm template picweight helm/picweight --values helm/picweight/ci/sealedsecret-values.yaml
helm install picweight helm/picweight --dry-run=client   # also renders NOTES.txt
```

### System dependencies

`pkg-config` and `libssl-dev`, and that is the whole list. SQLite is compiled
into the binary (`libsqlite3-sys` with `bundled`), so no `libsqlite3-dev`; there
is no ONNX and no ffmpeg, so none of phos's `libav*` / `clang` / `nasm` deps.

## Architecture

### Monorepo Layout

- **`backend/`** — Rust binary: axum 0.8, diesel 2 (sqlite + r2d2), rig 0.41,
  openidconnect 4, utoipa
- **`frontend/`** — Vue 3 SPA: Vite, Tailwind 4, shadcn-vue/reka-ui, lucide
- **`android/`** — Kotlin/Compose: Hilt, CameraX, ML Kit, Room, WorkManager,
  Retrofit generated from `android/openapi.json`
- **`helm/picweight/`** — the chart; **no `externalsecret.yaml`**, see below
- **`docs/`** — PRD and the rig spike

### Backend Modules (`backend/src/`)

- **`main.rs`** — process concerns only: config, logging, pool, OIDC handshake,
  workers, listener. Also the `openapi` subcommand
- **`lib.rs`** — `AppState`, `build_router`. The route table lives here, not in
  `main.rs`, so the integration suite exercises the wiring the binary serves
- **`config.rs`** — every `PICWEIGHT_*` variable
- **`auth.rs`** — OIDC discovery, cached JWKS, web (confidential) + mobile
  (public/native, PKCE) clients, session JWTs
- **`db.rs` / `models.rs` / `schema.rs`** — pool with WAL + busy_timeout,
  embedded migrations, diesel rows, `TEXT`-column enums
- **`error.rs`** — `AppError`; every failure serializes to one `ErrorBody` shape
- **`api/`** — `meals`, `groups`, `days`, `dishes`, `profile`, `weights`,
  `barcode`, `export`, `events` (SSE)
- **`agent/`** — the rig loop and **the swap boundary**: `mod.rs` (construction,
  `default_max_turns(6)`), `tools.rs`, `prompts.rs`, `schema.rs` (structured
  output), `session.rs` (serialize/resume, history cap, reseed rule),
  `reanalyze.rs`
- **`jobs/`** — `analyzer.rs` (one job → one loop → one revision),
  `group_settler.rs` (`group_size` hint + 90s debounce → one notification)
- **`food/openfoodfacts.rs`** — barcode lookups only
- **`nutrition/targets.rs`** — Mifflin-St Jeor
- **`feedback/`** — `state.rs` (rules engine), `phrasing.rs` (LLM wording with a
  templated fallback)
- **`storage/thumbs.rs`** — 768px content-addressed JPEGs

### Key Design Decisions

- **`rig`, not `rig-core`.** rig 0.41 split the run loop out of the core crate;
  `Agent`/`AgentRunner` exist only behind the facade. `max_turns` counts **model
  calls**, not tool calls — a two-tool run costs three.
- **Analysis is never inline.** `POST /api/v1/meals` returns `202`; a worker runs
  the loop; the client learns over SSE or by polling.
- **One photo = one meal = one loop.** `group_id` is a display and notification
  concern only. A solo meal is a group of one, so there is no special case.
- **The agent session is persisted and resumed, not restarted.** Correction by
  conversation continues the thread, so a fix costs one short turn instead of a
  second full loop with repeat tool calls.
- **Recall reads only the latest revision of `confirmed` meals.** Anything else
  teaches the agent from its own hallucinations.
- **Every user-scoped query filters `user_id`.** Another user's row is a 404, not
  a 403.
- **`client_uuid` is the idempotency key.** A replayed upload must never create a
  second meal — this is what makes the offline queue safe.
- **БЖУ comes from the model by design.** There is no dish-matching tool and no
  USDA seeding. Do not add one without re-reading PRD §1.3.
- **Targets are arithmetic, never an LLM.** Mifflin-St Jeor in
  `nutrition/targets.rs`.
- **Feedback is event-driven only.** No cron, no scheduled nudges. The only
  trigger is "you just logged something".
- **Originals are deleted.** One 768px thumbnail per meal, which doubles as the
  re-analysis input — do not shrink it.
- **The Helm chart never generates a Secret** and never assumes a secrets
  operator. It references existing Secrets by name and renders arbitrary
  user-supplied manifests through `additionalObjects`. CI asserts this. Do not
  add an `externalsecret.yaml`, however convenient it looks.

### Conventions

- No `unwrap()` / `expect()` / `panic!()` in request paths — use `AppError`.
- Public items get doc comments. `cargo clippy --all-targets` must be clean.
- Test names read as sentences (`a_replayed_client_uuid_creates_one_meal`).
- Comments explain *why*, especially where the code diverges from the obvious
  choice; the obvious choice is usually documented as rejected in the PRD.

## Reference Implementation

`/var/home/diverofdark/RustroverProjects/phos` is the same author's project with
the identical three-client shape (axum + Vue + Kotlin + Helm + CI). Port its
patterns rather than reinventing them — but note the deliberate divergences
listed in PRD §2, and two bugs that were fixed rather than inherited:

- phos uses `ServeDir::not_found_service` for the SPA fallback, which wraps the
  response in `SetStatus(404)`; every deep link becomes a 404 that happens to
  render. picweight uses `ServeDir::fallback`, which preserves the 200 — and
  therefore also needs the explicit `/api/**` JSON 404 route.
- `jsonwebtoken` 10 selects its crypto backend by crate feature; with default
  features the built-in provider *panics* on the first `encode`/`decode`. The
  `rust_crypto` feature is mandatory, not optional.
